# HAL Timebase Priority Fix / HAL 时基优先级修复

## Problem / 问题

After switching the HAL timebase source from SysTick to TIM7 (via CubeMX), the system
hung at `HAL_Delay()` — `uwTick` never incremented because the TIM7 interrupt never fired.

通过 CubeMX 将 HAL 时基从 SysTick 切换到 TIM7 后，系统在 `HAL_Delay()` 处卡死 —
`uwTick` 始终不增长，因为 TIM7 中断从未触发。

## Root Cause / 根因

The TIM7 interrupt priority was 15 (lowest), while DMA2_Stream5 and USART1 interrupts
were at priority 5. When the gray sensor DMA reception started, any USART error or DMA
event at priority 5 would continuously preempt TIM7 at priority 15, starving it indefinitely.

TIM7 中断优先级为 15（最低），而 DMA2_Stream5 和 USART1 中断优先级为 5。当灰色传感器
DMA 接收启动后，任何优先级 5 的 USART 错误或 DMA 事件都会持续抢占优先级 15 的 TIM7，
导致 TIM7 被无限饿死。

### Why was TIM7 at priority 15? / 为什么 TIM7 的优先级是 15？

`stm32f4xx_hal_timebase_tim.c` is generated by CubeMX from a template. The template uses
the `TickPriority` parameter passed to `HAL_InitTick()`:

`stm32f4xx_hal_timebase_tim.c` 由 CubeMX 从模板生成，模板直接使用传入 `HAL_InitTick()`
的 `TickPriority` 参数：

```c
HAL_NVIC_SetPriority(TIM7_IRQn, TickPriority, 0U);
uwTickPrio = TickPriority;
```

`TickPriority` originates from the HAL macro `TICK_INT_PRIORITY` (value 15), which matches
SysTick's default priority. CubeMX does not synchronize the NVIC panel setting (0) into
this template code — the two settings are independent and the template wins because
`HAL_InitTick` is called from `HAL_RCC_ClockConfig` **after** CubeMX's NVIC initialization.

`TickPriority` 来自 HAL 宏 `TICK_INT_PRIORITY`（值为 15），与 SysTick 默认优先级一致。
CubeMX 不会将 NVIC 面板中的设置（0）同步到此模板代码 — 两者互相独立，而模板代码优先，
因为 `HAL_InitTick` 从 `HAL_RCC_ClockConfig` 中调用，时间上**晚于** CubeMX 的 NVIC 初始化。

### Call sequence / 调用顺序

```
HAL_Init()
  └─ HAL_InitTick(15)         → TIM7 优先级设为 15, uwTickPrio = 15

SystemClock_Config()
  └─ HAL_RCC_ClockConfig()
       └─ HAL_InitTick(15)    → TIM7 优先级被覆盖回 15

MX_NVIC_Init()                 → CubeMX 将 TIM7 优先级设为 0（为时已晚）
```

## Fix / 修复

Changed `stm32f4xx_hal_timebase_tim.c` to use a fixed high priority instead of `TickPriority`:

将 `stm32f4xx_hal_timebase_tim.c` 中的优先级从 `TickPriority` 改为固定的最高优先级：

```c
HAL_NVIC_SetPriority(TIM7_IRQn, 0U, 0U);
uwTickPrio = 0U;
```

Priority 0 (highest) is safe because / 优先级 0（最高）是安全的，因为：

- The TIM7 ISR only calls `HAL_IncTick()` (`uwTick++`), a few cycles
  TIM7 中断只执行 `HAL_IncTick()`（即 `uwTick++`），几个时钟周期即返回
- It does not call any FreeRTOS API, so it is not subject to
  `configLIBRARY_MAX_SYSCALL_INTERRUPT_PRIORITY` (5)
  不调用任何 FreeRTOS API，不受 `configLIBRARY_MAX_SYSCALL_INTERRUPT_PRIORITY`(5) 约束
- FreeRTOS PendSV (15) and SysTick (15) are unaffected — TIM7 returns instantly
  FreeRTOS PendSV（15）和 SysTick（15）不受影响 — TIM7 瞬间返回

## Interrupt Priority Map / 中断优先级分布

| Priority / 优先级 | Interrupts / 中断                      |
|-------------------|----------------------------------------|
| 0                 | TIM7 (HAL timebase / HAL 时基)         |
| 5                 | DMA2_Stream5, USART1, CAN1, EXTI       |
| 6                 | EXTI0 (IST8310 DRDY)                   |
| 15                | SysTick (FreeRTOS), PendSV             |

## CubeMX Caveat / CubeMX 注意事项

When changing the HAL timebase source in CubeMX (SysTick → TIMx), CubeMX generates the
correct timer instance, IRQ handler, and callback, but does **not** update the priority
logic in `stm32f4xx_hal_timebase_tim.c`. The `TickPriority` parameter always resolves to
15 regardless of the NVIC panel setting. This must be fixed manually.

在 CubeMX 中切换 HAL 时基源（SysTick → TIMx）时，CubeMX 会正确生成定时器实例、
中断处理函数和回调函数，但**不会**更新 `stm32f4xx_hal_timebase_tim.c` 中的优先级逻辑。
`TickPriority` 参数始终解析为 15，无论 NVIC 面板中如何设置。此问题必须手动修复。
